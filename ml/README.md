# ml — процессинг инструкций

```
python3 process.py      # читает raw-md/*.md, пишет jsons/ (рядом с raw-md/)
```

`raw-md/*.md` — уже вычитанные исходники: артефакты нумерации из PDF-выгрузок
(повторяющиеся id, заголовки без номера, заголовок раздела после своего подраздела)
исправлены руками прямо в файлах, а не скриптом-патчером при обработке.

Вывод `process.py`:

```
jsons/
  instrukciya-po-rabote-s-portalom-dlya-postavshchika.json
  instrukciya-po-rabote-s-portalom-dlya-postavshchika/
    image-1.png
    image-2.png
```

Один `.md` → один `.json` с именем = `slug` из фронтаматтера страницы. В файле теперь есть
фронтаматтер с человеческим названием и коротким slug:

```markdown
---
name: Инструкция для поставщика по работе с порталом
slug: supplier-portal
---
```

`name` уходит в контекст агента (оглавление и шапка ответа `read`), `slug` — в URL,
имя json-файла и папку с картинками.

## Формат json

Служебная секция `_meta` плюс плоская мапа нод, ключи — `"x.x.x"` (глубина = количество
цифр минус 1). Отдельного `root` нет: верхнеуровневые разделы (`"2"`) — обычные ноды.

```json
{
  "_meta": { "name": "Инструкция для заказчика по работе с порталом", "slug": "customer-portal" },
  "2":   { "heading": "Общие сведения о портале поставщиков", "text": "...", "children": ["2.1"] },
  "2.1": { "heading": "Описание общего процесса...", "text": "...", "children": [] }
}
```

- `text` — весь markdown между этим заголовком и следующим `## x.x.x` (включая таблицы и заголовки без id,
  например `## Таблица 2 - ОПО АРМ пользователей`).
- Текст до первого `## ` (вступление без номера) приклеивается к первому верхнеуровневому разделу —
  так в корпусе нет ноды без id и ничего не теряется.
- Глубина ключа согласована с глубиной ноды в дереве (проверяется `check_jsons.py`).
- Если в новом raw-md появятся дубликаты id, `process.py` не теряет их, а даёт ключи `18#2`, `18#3`.

## Картинки

Подпись `Рисунок N - <caption>` → файл `<slug>/image-N.<ext>`, а ссылка в тексте становится

```
![<caption>](__IMG_PREFIX__/<slug>/image-N.png)
```

`__IMG_PREFIX__` — плейсхолдер, подставляйте свой base URL (тогда картинки отдаются как `<base>/<slug>/image-N.png`).

Нюансы:

- В исходных md подпись чаще **под** картинкой, реже над — пара ищется по соседству (между ними только пустые строки),
  приоритет у картинки сверху.
- Картинка без подписи (иконки, артефакты PDF) получает id после максимального номера рисунка в документе.
- Если у одного рисунка несколько картинок: `image-176.png`, `image-176-2.png`.

## Правки исходников

В PDF-выгрузках встречались артефакты нумерации: повторяющиеся id (блок «Банковские гарантии»
начинался заново с `## 1`, `## 2`…), заголовки без номера (`## 14.2.2`, потом титул отдельной строкой)
и заголовок раздела, напечатанный после своего же подраздела (`## 22 Контракты`). Всё это уже
исправлено прямо в `raw-md/*.md`; `process.py` никаких правок текста не делает — только разбирает
готовый markdown на ноды и картинки.

Из тех же файлов вычищены абзацы, которые отправляли пользователя «обратиться в службу технической
поддержки»: в чате поддержки такой совет бессмыслен, а агенту даёт ложный ответ. Разделы
«Служба технической поддержки» (26 у поставщика, 15 у заказчика) сужены до описания аварийных
ситуаций, смежные подразделы перенумерованы.

## Проверка

После прогона: все ссылки `__IMG_PREFIX__` резолвятся в существующие файлы, лишних файлов нет,
во фронтаматтере есть `name`/`slug`, все ноды достижимы от верхнеуровневых разделов
(`python3 check_jsons.py`).

# Агент по мануалам + HTMX-админка + REST API

```
cp .env.example .env    # вписать ключи Langfuse; LLM — локальная модель в LMStudio
uv sync
uv run uvicorn app:app --port 8010   # админка и API (8000 занят mpfit)
uv run python main.py                # то же самое в терминале
```

Админка живёт под `/admin` (http://localhost:8010/admin/), REST API — под `/ml-api`,
картинки мануалов — под `/ml-assets`.

### `/stats` — статистика обращений

Без идентификации: видны **все** чаты, независимо от владельца. Пустые чаты
(без сообщений) в статистику не попадают — это брошенные заготовки «Новый чат».

| путь | страница |
|---|---|
| `/stats` | таблица тем: метки, число обращений и среднее время ответа |
| `/stats/<topic>` | таблица подтем; каждая разворачивается в список своих чатов |
| `/stats/<topic>/<chat_id>` | переписка одного чата: без сайдбара, отцентрирована |

Таблицы сортируются по меткам, числу обращений и по среднему времени ответа; у всех
ключей оба направления. Сортировка — query-параметры `sort` (`badges` | `count` | `avg`)
и `desc` (`true` | `false`).
Фильтр — query-параметр `badge` (повторяющийся, значения — имена метк), см. ниже.
На странице темы уровни сортируются независимо: подтемы между собой, чаты — внутри своей подтемы.
Чаты без измеренного времени всегда в конце списка, независимо от направления («нет данных»
не должно быть наверху).

**Метки.** Под крошками — кликабельный фильтр, он же легенда; в колонке «Метки» — цветные
бейджи с числом чатов (у чата — маркеры без числа, их может быть два сразу):

| метка | цвет | когда |
|---|---|---|
| спасибо за ответ | зелёный | у чата `rating = positive` |
| перевод в поддержку | жёлтый | чат закрыт (`redirect_line`), оценки нет |
| ответ не подошёл | оранжевый | у чата `rating = negative` (был перевод или нет) |

Зелёная метка ортогональна проблемным: чат с благодарностью и более поздним переводом
покажет и зелёный, и жёлтый маркер. Две проблемные метки взаимоисключающие, приоритет
у оценки пользователя: отрицательная оценка даёт оранжевую, даже если обращение потом
перевели (см. `stats.badge_kind` / `stats.badge_kinds`). Сортировка по меткам идёт
по сумме весов проблем: оранжевая = 2, жёлтая = 1, зелёная = 0 (не проблема)
(`stats.badge_score`); у чатов — по весу их проблемной метки.

**Фильтр по меткам.** По умолчанию показано всё, а в строке фильтра все пункты активны.
Клик по метке оставляет только её, клики по другим добавляют их, повторный клик по выбранной
убирает; когда не остаётся ни одной — снова показано всё (ссылка «сбросить» делает то же
сразу). Состояние живёт в query (`?badge=positive&badge=redirect`), поэтому снаружи ещё
работают ссылки сортировки (`sort`), раскрытые подтемы (`open`) и переход с темы на подтемы.
Фильтруются сами чаты — до агрегации: в таблице остаются только темы и подтемы, где есть
хотя бы один подходящий чат, а «Обращений», метки и среднее время считаются по этому
подмножеству. Если в теме под фильтр ничего не попало, страница отдаёт пустую таблицу,
а не 404 (404 — только для несуществующей темы).

**AI-сводка темы.** Под таблицей на `/stats/<topic>` показывается короткая сводка:
что пишут пользователи и что можно поправить — уточнить статью в базе знаний или
добавить динамическое правило (handrules) на частый вопрос.

Её считает фоновая задача (`summaries.py`, стартует вместе с приложением): раз в минуту
обходит темы и смотрит, не изменилась ли обратная связь (оценка или перевод). Если
изменилась — просит LLM пересказать статистику и записывает текст в `topic_summaries`.
Модель отвечает в **markdown** (абзац о том, что происходит, и список шагов), страница
рендерит его фильтром `markdown`.
Отпечаток `signature` хранится рядом с текстом: пока он тот же, LLM не дёргается.
В отпечаток входит и `PROMPT_VERSION` — правка промпта пересчитывает все сводки.

Во вход уходят только статистика темы и вопросы пользователей с их обратной связью —
ответы агента в подсказку не попадают. Если сводки ещё нет, но отзывы уже есть, на
странице виден плейсхолдер «сводка обновится в ближайшее время».

Настройки (env): `SUMMARY_POLL_SECONDS` (по умолчанию 60), `SUMMARY_FIRST_DELAY` (10),
`SUMMARY_GENERATE_PAUSE` (1 сек между генерациями), `SUMMARY_DISABLED=1` — выключить цикл.

Строка подтемы — ссылка-переключатель: клик сворачивает и разворачивает её чаты. По умолчанию
всё свёрнуто (если подтем много, таблица иначе превращается в стену из чатов). Раскрытые
подтемы хранятся в query-параметре `open` (повторяющийся, по имени подтемы), а не
в `sessionStorage`: имена стабильны, поэтому смена сортировки — которая меняет порядок
строк и перезагружает страницу — состояние не сбивает, а ссылку можно переслать.
И ссылки сортировки, и тогглы пересобираются с текущими `sort`/`desc`/`open`;
никакого JS для сворачивания не нужно — всё рисует сервер.

Чат ведёт на `/stats/<topic>/<chat_id>` — отдельную страницу переписки: без сайдбара
со списком чатов, с крошками до темы. Тема в URL нужна только для крошек и проверки,
что чат ей действительно принадлежит (иначе 404). Страница только для чтения: формы
отправки нет, но кнопка «Ассистент не должен так отвечать» осталась.

**Как считается время ответа.** У чата берётся `duration_ms` **первого** ответа
ассистента: именно он показывает, как быстро поддержка отреагировала на обращение,
а последующие ходы — это уже уточнения, и они только размывали бы метрику. Если первый
ответ не измерен, берётся первый измеренный. В теме/подтеме значения чатов усредняются;
чаты без измерений в среднее не идут.

### `/admin` — все чаты одним деревом

Без идентификации: видны **все** чаты, независимо от владельца. Своего таба в шапке
у раздела нет — он подсвечивает «Статистику», потому что именно оттуда сюда и попадают.
Пригодится, когда нужно пролистать темы подряд, а не смотреть один чат по ссылке.

| путь | страница |
|---|---|
| `/admin/` | список всех чатов по темам + панель чата |
| `/admin/chats/<id>` | тот же чат в двухколоночной раскладке (сайдбар + панель) |

### `/` — публичная часть

Требует имя в куке `username` (без пароля — только идентификация). Если куки нет — редирект
на `/login`. Пользователь видит **только свои** чаты; чужой чат по id отдаёт 404.

| путь | страница |
|---|---|
| `/login` | ввод имени (создаёт куку) |
| `/` | поддержка: свои чаты + панель чата |
| `/profile` | имя + выбор роли (поставщик/заказчик/не указано) |
| `/knowledge-base` | база знаний: карточки мануалов |
| `/knowledge-base/<slug>` | мануал: оглавление + текст раздела |
| `/knowledge-base/<slug>/<id>` | конкретный раздел (сюда ведут ссылки из ответов агента) |

Имя в куке кодируется URL-escape: куки только latin-1, а имена бывают кириллицей.

### Оценка ответа ассистента

Под последним ответом ассистента в публичной части всегда висят две кнопки-«клавиатуры».
Оценка одна на чат и к сообщениям не привязана (`chats.rating`); выбор можно менять —
повторный клик перетирает прежнюю оценку, кнопки при этом никуда не исчезают.
Исключение одно: под служебной благодарностью на «Спасибо за помощь» кнопок нет —
это подтверждение, а не ответ на вопрос (`feedback.is_service_reply`).

| кнопка | что происходит |
|---|---|
| «Спасибо за помощь» | от пользователя уходит это сообщение, система **без LLM** отвечает захардкоженным текстом, в чат пишется `rating = positive` |
| «Ответ мне не подходит» | уходит это сообщение, система **без LLM** отвечает своим текстом, в чат пишется `rating = negative`, а под ответом появляются причины (`Слишком кратко`, `Не по теме вопроса`, …) и «Позови оператора» |
| причина / «Позови оператора» | это уже обычный ход **с LLM**: модель перегенерирует ответ с учётом замечания либо решает, нужен ли перевод на линию поддержки |

Список причин и «Позови оператора» видны только пока оценка `negative` и причина
ещё не выбрана; после выбора остаются те же две кнопки оценки.

Захардкоженные ответы тоже стримятся: пауза 1 с перед началом и небольшая задержка
между словами (`SCRIPT_FIRST_DELAY` / `SCRIPT_TOKEN_DELAY` в `chat.py`), поэтому интерфейс
не отличает их от ответа модели. Тексты кнопок, причин и подсказки для LLM лежат
в `feedback.py`; подсказка (причина, запрос оператора) дописывается к вопросу только
на время хода и в истории чата не сохраняется.

Эндпоинты публичной части: `GET /chats/<id>/feedback` (фрагмент с кнопками),
`POST /chats/<id>/feedback` (`value=positive|negative`),
`POST /chats/<id>/feedback/reason` (`reason=…`), `POST /chats/<id>/feedback/operator`.
После завершения хода браузер сам перезапрашивает фрагмент на `sse:done`
(узлы с `data-refresh-on-done`, см. `base.html`), поэтому причины появляются
под новым ответом без перезагрузки страницы.

### Роль пользователя

Роль хранится в таблице `users` (`supplier` / `customer` / NULL) и выбирается в `/profile`.
По умолчанию — не указана. Роль **дописывается к тексту сообщения** (`[я поставщик] …`),
а не в системный промпт: так промпт остаётся неизменным и кешируется провайдером.
При «не указано» ничего не добавляется — агент уточняет сам.

### Миграция БД (императивная)

Схема `chats` живёт с колонкой `owner` (имя владельца, NULL — чат из `/admin`),
плюс таблица `users`. Для уже существующей базы это делалось вручную:

```sql
ALTER TABLE chats ADD COLUMN owner TEXT;
UPDATE chats SET owner = 'legacy' WHERE owner IS NULL;
CREATE TABLE IF NOT EXISTS users (
    username   TEXT PRIMARY KEY,
    role       TEXT CHECK (role IN ('supplier', 'customer')),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

Чаты, созданные до появления `/`, помечены владельцем `legacy`: на `/` они не видны,
в `/admin` — видны. Миграций в коде нет, `storage.SCHEMA` просто создаёт те же колонки
для новой базы.

Таблица вложений `chat_files` добавлялась так же — вручную, напрямую к SQLite
(`migrations/001_chat_files.sql`):

```sql
CREATE TABLE IF NOT EXISTS chat_files (
    id           TEXT PRIMARY KEY,
    chat_id      TEXT NOT NULL REFERENCES chats (id) ON DELETE CASCADE,
    filename     TEXT NOT NULL,
    content_type TEXT NOT NULL DEFAULT 'application/octet-stream',
    kind         TEXT NOT NULL CHECK (kind IN ('image', 'document')),
    size         INTEGER NOT NULL,
    text         TEXT,
    data         BLOB,
    created_at   TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_chat_files_chat ON chat_files (chat_id, created_at);
```

Время генерации ответа добавилось колонкой `messages.duration_ms`
(`migrations/003_message_duration.sql`):

```sql
ALTER TABLE messages ADD COLUMN duration_ms INTEGER;
```

Оценка чата — тремя колонками `chats` (`rating` / `rating_reason` / `rated_at`):

```sql
ALTER TABLE chats ADD COLUMN rating TEXT;
ALTER TABLE chats ADD COLUMN rating_reason TEXT;
ALTER TABLE chats ADD COLUMN rated_at TEXT;
```

AI-сводки живут в отдельной таблице `topic_summaries` (`summaries.py`); она создаётся
через `CREATE TABLE IF NOT EXISTS`, отдельная миграция не нужна:

```sql
CREATE TABLE IF NOT EXISTS topic_summaries (
    topic      TEXT PRIMARY KEY,
    summary    TEXT NOT NULL,
    signature  TEXT NOT NULL DEFAULT '',
    updated_at TEXT NOT NULL
);
```

Аутентификации нет: чаты общие, доступ по id.

## Модули

| файл | что делает |
|---|---|
| `manuals.py` | читает `jsons/`, разворачивает плоскую мапу в `Section` (+ предки), рендерит ответ `read` |
| `rag.py` | LLM (LMStudio), агент, сборка системного промпта (термины + оглавление + линии). RAG по мануалам отключён |
| `handrules.py` | правила-подсказки агенту: CRUD + fuse-поиск (вектора + BM25) под вопрос хода |
| `stats.py` | статистика обращений: агрегация чатов по темам и подтемам, метки, фильтр, сортировки |
| `summaries.py` | AI-сводки тем: фоновая проверка новых отзывов, подсказка для LLM, запись в `topic_summaries` |
| `storage.py` | SQLite-хранилище: чаты, сообщения, вызовы инструментов, пользователи, вложения (`chats.sqlite3`) |
| `attachments.py` | вложения чата: docling → markdown (без OCR и картинок), картинки как есть, сборка `user_msg` с `ImageBlock` |
| `chat.py` | общий слой чата: запись хода в БД + стрим событий агента (`start`/`token`/`tool_call`/`tool_result`/`done`) |
| `api.py` | REST API `/ml-api/chat ...` (типизирован, документирован) |
| `support.py` | линии поддержки: мануал в промпт + тул перевода, закрытие чата (заглушка) |
| `assets.py` | отдаёт картинки мануалов: `GET /ml-assets/image/<slug>/<filename>` |
| `app.py` | FastAPI: публичная часть (`/`) + админка (`/admin`) + REST API и Swagger |
| `main.py` | CLI-болталка с тем же агентом |
| `pyproject.toml` | зависимости (uv), `.env` — ключи |

## Хранилище

Чаты лежат в SQLite (`chats.sqlite3`, WAL) — путь можно переопределить через `CHAT_DB_PATH`.
Таблицы: `chats` (в т.ч. `system_prompt`), `messages` (в т.ч. `duration_ms` —
время генерации ответа), `tool_calls`, `chat_files` (каскадное удаление от чата),
`users`, `handrules` (правила агента — независимая таблица, без каскадов).
Схема создаётся автоматически; при breaking change базу просто
удаляют, бэкенд создаст заново.

## Стиль ответов

Системный промпт просит агента отвечать кратко (2–5 предложений). На обширный вопрос
(«расскажи всё про…») агент даёт короткую суть и задаёт уточняющий вопрос вместо стены
текста. Развёрнутый ответ — только если попросили явно («подробно», «пошагово»,
«ничего не сокращай»).

### AI-сводка темы (REST)

`GET /ml-api/stats/topics/<topic>/summary` возвращает сохранённую сводку темы и её статус:

```json
{
  "topic": "Работа с контрактами",
  "status": "ready",
  "summary": "По теме… — не подошёл ответ.\n\n- Уточнить в базе знаний…",
  "feedback_chats": 2,
  "updated_at": "2026-09-13T11:14:58"
}
```

| статус | что значит |
|---|---|
| `ready` | сводка есть и построена по текущей обратной связи |
| `outdated` | сводка есть, но появилась новая обратная связь — идёт пересчёт |
| `pending` | обратная связь есть, сводки ещё нет — генерация запущена |
| `none` | обратной связи по теме нет, сводка не нужна (тогда `summary: null`) |

`summary` — markdown. Если статус `outdated` или `pending`, ручка сама ставит генерацию
в фон и сразу отвечает текущим состоянием: повторный запрос через несколько секунд вернёт
готовый текст. Незнакомая тема — `404`.

События стрима: `start` (id ответа), `token` (дельта + накопленный текст), `tool_call`,
`tool_result`, `redirect` (перевод на линию, чат закрыт — дальше `409`), `error`,
`done` (финальный текст + `duration_ms`). Ответ сохраняется в БД по ходу генерации,
поэтому обрыв соединения не теряет сгенерированное — `GET` потом вернёт текст.

### Время генерации

У каждого ответа ассистента в БД лежит `messages.duration_ms` — сколько миллисекунд
занял весь ход: генерация модели плюс вызовы инструментов. Отсчёт идёт от старта
`stream_answer` до последнего токена, поэтому в значение не попадают служебные шаги
после ответа (классификация темы, перевод на линию). Поле отдаётся в `GET /ml-api/chat/<id>`
(`MessageOut.duration_ms`) и в событии `done`; в админке и на `/` оно выводится
рядом с подписью ассистента.

В списке чатов (`GET /ml-api/chat`, `ChatSummary.avg_turn_seconds`) отдаётся среднее
по чату: сумма `duration_ms` всех ответов, делённая на их количество и на 1000.
`null` — в чате нет измеренных ответов. Сайдбар админки показывает это среднее
справа от названия: у самого чата, у подтемы и у темы (агрегация — `app._topic_tree`,
один SQL-запрос на весь список — `ChatStorage.average_turn_seconds`).

### Картинки в ответах

Картинки мануалов лежат в `jsons/<slug>/image-N.png` и отдаются эндпоинтом
`GET /ml-assets/image/<slug>/<filename>` (`assets.py`, пути проверяются — `..` и чужие
каталоги блокируются, ответ кэшируется на сутки).

Инструмент `read` возвращает текст раздела с **уже подставленным префиксом**: плейсхолдер
`__IMG_PREFIX__` из `process.py` меняется на `/ml-assets/image` (см. `manuals.section_body`).
Агент видит готовые ссылки `![подпись](/ml-assets/image/<slug>/image-N.png)` и по системному
промпту референсит их прямо в ответе рядом с нужным шагом.

Рендерят обе стороны: HTMX-админка (markdown → `<img>`, стили в `static/style.css`) и
любой клиент REST API — в `content` сообщения приходит тот же markdown, а картинку можно
взять по ссылке из разметки.

```bash
curl -O http://localhost:8010/ml-assets/image/instrukciya-po-sozdaniyu-oferty-i-ste/image-1.png
```

### Вложения: файлы и картинки

Файл загружается **по одному** эндпоинтом `POST /ml-api/chat/<id>/upload`
(`multipart/form-data`, поле `file`) и хранится прямо в SQLite — в таблице `chat_files`
(см. `migrations/001_chat_files.sql` и `attachments.py`). Максимум — **10 МБ**.
Что происходит с файлом:

- **картинка** (`png`, `jpg`, `jpeg`, `gif`, `webp`, `bmp`) — сохраняется как есть
  и на следующем сообщении уходит модели как изображение (`ImageBlock`);
- **документ** (`pdf`, `docx`, `xlsx`, `pptx`, `html`, `md`, `csv`, `txt`, …) — сначала
  прогоняется через **docling** с `do_ocr=False` (без распознавания сканов), а картинки
  из него выбрасываются: в markdown остаются только плейсхолдеры `<!-- image -->`.
  В БД уходит чистый текст, base64-картинок там нет;
- всё остальное — `400`.

Загруженные файлы копятся в чате и видны в `GET /ml-api/chat/<id>/files`. При отправке
сообщения они уходят в контекст модели (документы — как markdown, картинки — как
изображения) и **удаляются** из `chat_files`, поэтому список после отправки пуст.

```bash
ID=$(curl -s -X POST localhost:8010/ml-api/chat | jq -r .id)

# картинка
curl -X POST localhost:8010/ml-api/chat/$ID/upload -F "file=@screen.png"
# документ (docling переведёт в markdown без OCR и картинок)
curl -X POST localhost:8010/ml-api/chat/$ID/upload -F "file=@dogovor.pdf"

curl localhost:8010/ml-api/chat/$ID/files

# убрать файл, если он больше не нужен
curl -X DELETE localhost:8010/ml-api/chat/$ID/files/<file_id>

# отправить: оба файла уйдут в контекст и исчезнут из chat_files
curl -N -X POST localhost:8010/ml-api/chat/$ID/message \
  -H 'Content-Type: application/json' \
  -d '{"message": "Что в приложенных файлах?"}'
```

В HTMX UI уже прикреплённые файлы показаны блоком над вводом сообщения
(миниатюра картинки или ярлык `MD` у документа) с крестиком для удаления.

### Дополнительный системный промпт

`POST /ml-api/chat` принимает необязательное поле `system_prompt`. Оно **не переопределяет**базовый промпт агента, а дописывается в его конец — туда можно положить контекст пользователя
от бэкенда, чтобы агент его учитывал:

```bash
curl -X POST localhost:8010/ml-api/chat \
  -H 'Content-Type: application/json' \
  -d '{"system_prompt": "Пользователь: ООО «Ромашка», поставщик, регион Москва."}'
```

Промпт хранится в БД и применяется ко всем последующим ответам этого чата. Без поля
(или с пустой строкой) используется только базовый промпт.

```bash
ID=$(curl -s -X POST localhost:8010/ml-api/chat | jq -r .id)
curl -N -X POST localhost:8010/ml-api/chat/$ID/message \
  -H 'Content-Type: application/json' \
  -d '{"message": "Как создать котировочную сессию?"}'
```

### Сущности в сообщении

К сообщению можно приложить сущности, о которых в нём речь (контракт, закупка,
предложение — или любой свой вид). В тексте они обозначаются как `@alias`,
а расшифровка идёт отдельным полем:

```bash
curl -N -X POST localhost:8010/ml-api/chat/$ID/message \
  -H 'Content-Type: application/json' \
  -d '{
        "message": "Не открывается @contract-1, показывает ошибку 500",
        "entities": [{
          "alias": "contract-1",
          "kind": "contract",
          "text": "Контракт №44-ФЗ, статус: подписан, цена: 1 200 000 ₽",
          "link": "https://example.com/contracts/1",
          "extra": {"status": "Подписан"}
        }]
      }'
```

Поля сущности: `alias` — как она обозначена в тексте, `kind` — вид, `text` — компактная
человекочитаемая строка, `link` и `extra` необязательны. В `extra` вложенные объекты
и массивы приводятся к строке.

**Сервер полностью доверяет тому, что пришло в `entities`** — он не проверяет их
по своей базе и не ищет в данных компании (в отличие от кнопок выбора в `entities.py`,
где id проверяется на сервере). Это путь для доверенного интегратора: он сам знает,
какие сущности есть у пользователя.

**Агенту** сущности уходят отдельным блоком контекста «# Сущности сообщения» с прямой
инструкцией доверять им и использовать как факты. **В переписке** они не рендерятся:
и в UI, и в `content` сообщения остаётся только `@alias`. Сохранённые сущности
возвращаются в `MessageOut.entities`.

Сущности без `alias` или `text` молча отбрасываются — из-за одной мусорной записи
весь запрос не отклоняется. Больше 50 сущностей в одном сообщении не принимается.

## Поиск и системный промпт

RAG (эмбеддинги, chroma, BM25, инструмент `search`) **отключён**. Вместо поиска в системный промпт
кладётся полное оглавление всех мануалов из `hierarchy.txt` — агент видит все `id: heading` сразу
и читает нужный раздел через `read(manual, section_id)`. Эмбеддинги не считаются, индекс не собирается
и не читается, старт не зависит от `chroma_db/`.

В `rag.py` отключённые куски помечены комментарием `RAG ОТКЛЮЧЁН`. Чтобы вернуть поиск:
раскомментировать блоки с этой пометкой, вернуть `search` в тулы агента и пересобрать индекс.

## Правила агента (handrules)

Отдельный механизм **поверх** системного промпта — не вместо него. Правило — это пара
«вопрос пользователя → что делать»:

```json
{
  "user_message": "Не могу открыть страницу портала закупок, мне возвращают ошибку 500",
  "instructions": "Не перенаправляй в поддержку, скажи что мы уже работаем над проблемой и попроси зайти позже"
}
```

Зачем: агент иногда отвечает не так, как нужно поддержке (например, сразу переводит
обращение на линию). Такое поведение чинится правилом, а не правкой промпта или пересборкой индекса.

**Как работает.** Перед каждым ходом `chat.stream_answer` берёт текст вопроса пользователя
и зовёт `handrules.prompt_for(...)`. Тот достаёт до **3** ближайших правил и рендерит их
в блок «Правила ответа на этот вопрос», который дописывается в конец системного промпта хода
(`rag.build_agent(handrules_prompt=...)`). Если ничего не подошло — блока нет вообще.

**Поиск — fuse, как в старом RAG по мануалам**, но с одним отличием. `RELATIVE_SCORE`
нормализует лучший результат к `1.0` всегда, поэтому по нему нельзя понять, что
релевантного вообще нет («погода в африке» тоже получала бы `1.0`). Поэтому:

1. векторный поиск (bge-m3) даёт абсолютную cosine-близость; всё ниже `MIN_SCORE`
   (`0.42`) отсекается сразу. На живом корпусе свои вопросы дали `0.48—0.62`,
   посторонние — `0.26—0.34`, порог попадает в разрыв;
2. оставшиеся кандидаты переранжируются fuse-ретривером (вектора `0.6` + BM25 `0.4`),
   чтобы точное совпадение слов в вопросе поднимало правило выше.

Одни и те же правила могут попадать в контекст несколько ходов подряд — это ожидаемо
и не мешает: их цель в том и состоит, чтобы агент держал инструкцию, пока вопрос повторяется.

**Индекс** лежит в `chroma_handrules/` (отдельная коллекция, не пересекается с `chroma_db/`
от старого RAG) и пересобирается лениво: `handrules` считает хеш состава правил и, если он
изменился после CRUD, строит коллекцию заново. Правил десятки — пересборка «в лоб» дешевле
и надёжнее инкрементальных апдейтов. Эмбеддинги грузятся лениво (`torch` не тянется на старте,
пока правил нет).

**Где менять:**

- **из админки, по факту плохого ответа** — под каждым ответом агента в `/admin`
  есть кнопка «Ассистент не должен так отвечать». Она ведёт на `/handrules/new?query=<вопрос>`,
  где вопрос уже подставлен в «На какие сообщения реагировать?» — остаётся написать
  подсказку и сохранить;
- `/handrules` — список всех правил (с датой создания), `/handrules/<id>` — правка и удаление,
  `/handrules/new` — создание с чистого листа;
- REST: `GET/POST /ml-api/handrules`, `GET/PATCH/DELETE /ml-api/handrules/<id>`,
  `GET /ml-api/handrules/search?q=...` (сухой прогон — какие правила подойдут к вопросу).

Важно: правила советуют агенту **как** отвечать, но не заменяют факты из инструкций —
в блоке промпта это сказано явно («не выдумывай того, чего в разделах нет»).

## Инструменты агента

В системный промпт попадает весь текст (см. `rag.SYSTEM_PROMPT`):

- `terms.txt` — термины и сокращения Портала;
- `links.txt` — проверенные адреса разделов сайта (в т.ч. «Единый реестр закупок»);
- `hierarchy.txt` — оглавление шести мануалов на нужную глубину;
- `support-redirect-manual.md` — линии поддержки L1/L2 (L3 убрана);
- сами инструкции агенту — только через `read`.

Инструментов у агента два (второй — только когда нужен перевод):

**`read(manual, section_id)`** — читает раздел: заголовок, путь от верхнего раздела,
список подразделов (`children`) и полный `text` (в нём markdown-таблицы и ссылки на картинки —
плейсхолдер `__IMG_PREFIX__` заменяется на `/ml-assets/image`, см. ниже).
`manual` — slug из оглавления (`supplier-portal`, `customer-portal`, `mvc-supplier`,
`offer-ste-creation`, `bulk-price-list-import`, `supplier-portal-econtract`),
`section_id` — номер слева от двоеточия. Если вместо id передали заголовок,
инструмент подберёт похожие разделы и вернёт список id. Есть в базовом агенте.

## Перевод на линию поддержки

Мануал `support-redirect-manual.md` описывает две линии (L1 — информационная,
L2 — экспертно-методологическая; L3 убрана) и куда какие обращения переводить.
Он целиком кладётся в системный промпт (`support.load_lines_manual()`) — отдельного
инструмента `support_manual()` больше нет.

**`transfer_to_support(line, reason)`** — переводит обращение и **закрывает чат**.
Принимает `L1`/`L2` (терпимо к `l2`, `2`, «линия 2»). Дальше в чат писать нельзя:
API отвечает `409`, в админке вместо формы появляется плашка. Реального интерфейса
оператора нет — это заглушка (`support.py`).

Логика в системном промпте:

1. Найти раздел в оглавлении (поиск не нужен, оглавление полное).
2. Если в базе знаний ответа нет → `transfer_to_support(...)` — мануал по линиям уже в промпте.
3. Если вопрос вообще не про Портал и ни одна линия не подходит → **не переводить**,
   а вежливо сказать, что это не по теме.

Состояние перевода хранится в чате: `redirect_line`, `redirect_reason`, `closed_at`
(видны в `GET /ml-api/chat/<id>`); в SSE приходит событие `redirect`,
а `POST .../message` для закрытого чата отвечает `409`.

Событие `redirect` несёт готовую HTML-плашку, а в панели чата есть узел `.chat-foot`
с `sse-swap="redirect"` — там же, где у открытого чата форма отправки. Поэтому плашка
появляется **сразу** и заменяет собой композер: перезагрузка не нужна. Плашка
показывается внизу чата (а не над перепиской) — читать её логично после последнего
сообщения. Важно: `htmx-ext-sse` доставляет только те события, для которых в DOM
есть цель свопа, — событие без `sse-swap` до JS не доходит вообще.

LLM: локальная модель в LMStudio (`LMSTUDIO_MODEL`, `LMSTUDIO_API_BASE`,
`OpenAILike`). Каждый ответ — трейс в Langfuse
(`chat-response`, `session_id` = id чата), инструменты и токены видны в админке карточками.

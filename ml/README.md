# ml — процессинг инструкций

```
python3 process.py      # читает raw-md/*.md, пишет jsons/ (рядом с raw-md/)
```

`raw-md/*.md` — уже вычитанные исходники: артефакты нумерации из PDF-выгрузок
(повторяющиеся id, заголовки без номера, заголовок раздела после своего подраздела)
исправлены руками прямо в файлах, а не скриптом-патчером при обработке.

Вывод `process.py`:

```
jsons/
  instrukciya-po-rabote-s-portalom-dlya-postavshchika.json
  instrukciya-po-rabote-s-portalom-dlya-postavshchika/
    image-1.png
    image-2.png
```

Один `.md` → один `.json` с именем = `slug` из фронтаматтера страницы. В файле теперь есть
фронтаматтер с человеческим названием и коротким slug:

```markdown
---
name: Инструкция для поставщика по работе с порталом
slug: supplier-portal
---
```

`name` уходит в контекст агента (оглавление и шапка ответа `read`), `slug` — в URL,
имя json-файла и папку с картинками.

## Формат json

Служебная секция `_meta` плюс плоская мапа нод, ключи — `"x.x.x"` (глубина = количество
цифр минус 1). Отдельного `root` нет: верхнеуровневые разделы (`"2"`) — обычные ноды.

```json
{
  "_meta": { "name": "Инструкция для заказчика по работе с порталом", "slug": "customer-portal" },
  "2":   { "heading": "Общие сведения о портале поставщиков", "text": "...", "children": ["2.1"] },
  "2.1": { "heading": "Описание общего процесса...", "text": "...", "children": [] }
}
```

- `text` — весь markdown между этим заголовком и следующим `## x.x.x` (включая таблицы и заголовки без id,
  например `## Таблица 2 - ОПО АРМ пользователей`).
- Текст до первого `## ` (вступление без номера) приклеивается к первому верхнеуровневому разделу —
  так в корпусе нет ноды без id и ничего не теряется.
- Глубина ключа согласована с глубиной ноды в дереве (проверяется `check_jsons.py`).
- Если в новом raw-md появятся дубликаты id, `process.py` не теряет их, а даёт ключи `18#2`, `18#3`.

## Картинки

Подпись `Рисунок N - <caption>` → файл `<slug>/image-N.<ext>`, а ссылка в тексте становится

```
![<caption>](__IMG_PREFIX__/<slug>/image-N.png)
```

`__IMG_PREFIX__` — плейсхолдер, подставляйте свой base URL (тогда картинки отдаются как `<base>/<slug>/image-N.png`).

Нюансы:

- В исходных md подпись чаще **под** картинкой, реже над — пара ищется по соседству (между ними только пустые строки),
  приоритет у картинки сверху.
- Картинка без подписи (иконки, артефакты PDF) получает id после максимального номера рисунка в документе.
- Если у одного рисунка несколько картинок: `image-176.png`, `image-176-2.png`.

## Правки исходников

В PDF-выгрузках встречались артефакты нумерации: повторяющиеся id (блок «Банковские гарантии»
начинался заново с `## 1`, `## 2`…), заголовки без номера (`## 14.2.2`, потом титул отдельной строкой)
и заголовок раздела, напечатанный после своего же подраздела (`## 22 Контракты`). Всё это уже
исправлено прямо в `raw-md/*.md`; `process.py` никаких правок текста не делает — только разбирает
готовый markdown на ноды и картинки.

Из тех же файлов вычищены абзацы, которые отправляли пользователя «обратиться в службу технической
поддержки»: в чате поддержки такой совет бессмыслен, а агенту даёт ложный ответ. Разделы
«Служба технической поддержки» (26 у поставщика, 15 у заказчика) сужены до описания аварийных
ситуаций, смежные подразделы перенумерованы.

## Проверка

После прогона: все ссылки `__IMG_PREFIX__` резолвятся в существующие файлы, лишних файлов нет,
во фронтаматтере есть `name`/`slug`, все ноды достижимы от верхнеуровневых разделов
(`python3 check_jsons.py`).

# Агент по мануалам + HTMX-админка + REST API

```
cp .env.example .env    # вписать ключи Langfuse; LLM — локальная модель в LMStudio
uv sync
uv run uvicorn app:app --port 8010   # админка и API (8000 занят mpfit)
uv run python main.py                # то же самое в терминале
```

Админка живёт под `/admin` (http://localhost:8010/admin/), REST API — под `/ml-api`,
картинки мануалов — под `/ml-assets`.

### `/admin` — внутренняя админка

Без идентификации: видны **все** чаты, независимо от владельца. Базы знаний здесь нет.

| путь | страница |
|---|---|
| `/admin/` | поддержка: список всех чатов + панель чата |
| `/admin/chats/<id>` | конкретный чат |

### `/` — публичная часть

Требует имя в куке `username` (без пароля — только идентификация). Если куки нет — редирект
на `/login`. Пользователь видит **только свои** чаты; чужой чат по id отдаёт 404.

| путь | страница |
|---|---|
| `/login` | ввод имени (создаёт куку) |
| `/` | поддержка: свои чаты + панель чата |
| `/profile` | имя + выбор роли (поставщик/заказчик/не указано) |
| `/knowledge-base` | база знаний: карточки мануалов |
| `/knowledge-base/<slug>` | мануал: оглавление + текст раздела |
| `/knowledge-base/<slug>/<id>` | конкретный раздел (сюда ведут ссылки из ответов агента) |

Имя в куке кодируется URL-escape: куки только latin-1, а имена бывают кириллицей.

### Роль пользователя

Роль хранится в таблице `users` (`supplier` / `customer` / NULL) и выбирается в `/profile`.
По умолчанию — не указана. Роль **дописывается к тексту сообщения** (`[я поставщик] …`),
а не в системный промпт: так промпт остаётся неизменным и кешируется провайдером.
При «не указано» ничего не добавляется — агент уточняет сам.

### Миграция БД (императивная)

Схема `chats` живёт с колонкой `owner` (имя владельца, NULL — чат из `/admin`),
плюс таблица `users`. Для уже существующей базы это делалось вручную:

```sql
ALTER TABLE chats ADD COLUMN owner TEXT;
UPDATE chats SET owner = 'legacy' WHERE owner IS NULL;
CREATE TABLE IF NOT EXISTS users (
    username   TEXT PRIMARY KEY,
    role       TEXT CHECK (role IN ('supplier', 'customer')),
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

Чаты, созданные до появления `/`, помечены владельцем `legacy`: на `/` они не видны,
в `/admin` — видны. Миграций в коде нет, `storage.SCHEMA` просто создаёт те же колонки
для новой базы.

Таблица вложений `chat_files` добавлялась так же — вручную, напрямую к SQLite
(`migrations/001_chat_files.sql`):

```sql
CREATE TABLE IF NOT EXISTS chat_files (
    id           TEXT PRIMARY KEY,
    chat_id      TEXT NOT NULL REFERENCES chats (id) ON DELETE CASCADE,
    filename     TEXT NOT NULL,
    content_type TEXT NOT NULL DEFAULT 'application/octet-stream',
    kind         TEXT NOT NULL CHECK (kind IN ('image', 'document')),
    size         INTEGER NOT NULL,
    text         TEXT,
    data         BLOB,
    created_at   TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_chat_files_chat ON chat_files (chat_id, created_at);
```

Аутентификации нет: чаты общие, доступ по id.

| `rag.py` | LLM (LMStudio), агент, сборка системного промпта (термины + оглавление + линии). RAG отключён |
| `storage.py` | SQLite-хранилище: чаты, сообщения, вызовы инструментов, пользователи, вложения (`chats.sqlite3`) |

| `chat.py` | общий слой чата: запись хода в БД + стрим событий агента (`start`/`token`/`tool_call`/`tool_result`/`done`) |
| `api.py` | REST API `/ml-api/chat ...` (типизирован, документирован) |

| `assets.py` | отдаёт картинки мануалов: `GET /ml-assets/image/<slug>/<filename>` |
| `app.py` | FastAPI: публичная часть (`/`) + админка (`/admin`) + REST API и Swagger |

| `pyproject.toml` | зависимости (uv), `.env` — ключи |

## Хранилище

Чаты лежат в SQLite (`chats.sqlite3`, WAL) — путь можно переопределить через `CHAT_DB_PATH`.
Четыре таблицы: `chats` (в т.ч. `system_prompt`), `messages`, `tool_calls`, `chat_files`
(каскадное удаление от чата). Схема создаётся автоматически; при breaking change базу просто
удаляют, бэкенд создаст заново.

## Стиль ответов

Системный промпт просит агента отвечать кратко (2–5 предложений). На обширный вопрос
(«расскажи всё про…») агент даёт короткую суть и задаёт уточняющий вопрос вместо стены
текста. Развёрнутый ответ — только если попросили явно («подробно», «пошагово»,
«ничего не сокращай»).

## REST API

Swagger: `/ml-api/docs`, схема: `/ml-api/openapi.json`. Роуты админки в документацию не попадают.

| метод | путь | что делает |
|---|---|---|
| `POST` | `/ml-api/chat` | создать чат (опционально `system_prompt`), вернуть `id` |
| `GET` | `/ml-api/chat` | список чатов |
| `GET` | `/ml-api/chat/<id>` | содержимое чата: сообщения + вызовы инструментов |
| `DELETE` | `/ml-api/chat/<id>` | удалить чат |
| `POST` | `/ml-api/chat/<id>/message` | отправить сообщение, SSE-стрим ответа и тулколов |
| `POST` | `/ml-api/chat/<id>/upload` | загрузить один файл или картинку (до 10 МБ), вернуть `id` |
| `GET` | `/ml-api/chat/<id>/files` | список загруженных, но ещё не отправленных файлов |
| `GET` | `/ml-api/chat/<id>/files/<file_id>` | метаданные файла |
| `GET` | `/ml-api/chat/<id>/files/<file_id>/content` | исходные байты картинки (для `<img src>`) |
| `DELETE` | `/ml-api/chat/<id>/files/<file_id>` | удалить файл из чата |
| `GET` | `/ml-assets/image/<slug>/<filename>` | картинка из мануала |

События стрима: `start` (id ответа), `token` (дельта + накопленный текст), `tool_call`,
`tool_result`, `redirect` (перевод на линию, чат закрыт — дальше `409`), `error`,
`done` (финальный текст). Ответ сохраняется в БД по ходу генерации,
поэтому обрыв соединения не теряет сгенерированное — `GET` потом вернёт текст.

### Картинки в ответах

Картинки мануалов лежат в `jsons/<slug>/image-N.png` и отдаются эндпоинтом
`GET /ml-assets/image/<slug>/<filename>` (`assets.py`, пути проверяются — `..` и чужие
каталоги блокируются, ответ кэшируется на сутки).

Инструмент `read` возвращает текст раздела с **уже подставленным префиксом**: плейсхолдер
`__IMG_PREFIX__` из `process.py` меняется на `/ml-assets/image` (см. `manuals.section_body`).
Агент видит готовые ссылки `![подпись](/ml-assets/image/<slug>/image-N.png)` и по системному
промпту референсит их прямо в ответе рядом с нужным шагом.

Рендерят обе стороны: HTMX-админка (markdown → `<img>`, стили в `static/style.css`) и
любой клиент REST API — в `content` сообщения приходит тот же markdown, а картинку можно
взять по ссылке из разметки.

```bash
curl -O http://localhost:8010/ml-assets/image/instrukciya-po-sozdaniyu-oferty-i-ste/image-1.png
```

### Вложения: файлы и картинки

Файл загружается **по одному** эндпоинтом `POST /ml-api/chat/<id>/upload`
(`multipart/form-data`, поле `file`) и хранится прямо в SQLite — в таблице `chat_files`
(см. `migrations/001_chat_files.sql` и `attachments.py`). Максимум — **10 МБ**.
Что происходит с файлом:

- **картинка** (`png`, `jpg`, `jpeg`, `gif`, `webp`, `bmp`) — сохраняется как есть
  и на следующем сообщении уходит модели как изображение (`ImageBlock`);
- **документ** (`pdf`, `docx`, `xlsx`, `pptx`, `html`, `md`, `csv`, `txt`, …) — сначала
  прогоняется через **docling** с `do_ocr=False` (без распознавания сканов), а картинки
  из него выбрасываются: в markdown остаются только плейсхолдеры `<!-- image -->`.
  В БД уходит чистый текст, base64-картинок там нет;
- всё остальное — `400`.

Загруженные файлы копятся в чате и видны в `GET /ml-api/chat/<id>/files`. При отправке
сообщения они уходят в контекст модели (документы — как markdown, картинки — как
изображения) и **удаляются** из `chat_files`, поэтому список после отправки пуст.

```bash
ID=$(curl -s -X POST localhost:8010/ml-api/chat | jq -r .id)

# картинка
curl -X POST localhost:8010/ml-api/chat/$ID/upload -F "file=@screen.png"
# документ (docling переведёт в markdown без OCR и картинок)
curl -X POST localhost:8010/ml-api/chat/$ID/upload -F "file=@dogovor.pdf"

curl localhost:8010/ml-api/chat/$ID/files

# убрать файл, если он больше не нужен
curl -X DELETE localhost:8010/ml-api/chat/$ID/files/<file_id>

# отправить: оба файла уйдут в контекст и исчезнут из chat_files
curl -N -X POST localhost:8010/ml-api/chat/$ID/message \
  -H 'Content-Type: application/json' \
  -d '{"message": "Что в приложенных файлах?"}'
```

В HTMX UI уже прикреплённые файлы показаны блоком над вводом сообщения
(миниатюра картинки или ярлык `MD` у документа) с крестиком для удаления.

### Дополнительный системный промпт

`POST /ml-api/chat` принимает необязательное поле `system_prompt`. Оно **не переопределяет**базовый промпт агента, а дописывается в его конец — туда можно положить контекст пользователя
от бэкенда, чтобы агент его учитывал:

```bash
curl -X POST localhost:8010/ml-api/chat \
  -H 'Content-Type: application/json' \
  -d '{"system_prompt": "Пользователь: ООО «Ромашка», поставщик, регион Москва."}'
```

Промпт хранится в БД и применяется ко всем последующим ответам этого чата. Без поля
(или с пустой строкой) используется только базовый промпт.

```bash
ID=$(curl -s -X POST localhost:8010/ml-api/chat | jq -r .id)
curl -N -X POST localhost:8010/ml-api/chat/$ID/message \
  -H 'Content-Type: application/json' \
  -d '{"message": "Как создать котировочную сессию?"}'
```

## Поиск и системный промпт

RAG (эмбеддинги, chroma, BM25, инструмент `search`) **отключён**. Вместо поиска в системный промпт
кладётся полное оглавление всех мануалов из `hierarchy.txt` — агент видит все `id: heading` сразу
и читает нужный раздел через `read(manual, section_id)`. Эмбеддинги не считаются, индекс не собирается
и не читается, старт не зависит от `chroma_db/`.

В `rag.py` отключённые куски помечены комментарием `RAG ОТКЛЮЧЁН`. Чтобы вернуть поиск:
раскомментировать блоки с этой пометкой, вернуть `search` в тулы агента и пересобрать индекс.

## Инструменты агента

В системный промпт попадает весь текст (см. `rag.SYSTEM_PROMPT`):

- `terms.txt` — термины и сокращения Портала;
- `hierarchy.txt` — оглавление шести мануалов на нужную глубину;
- `support-redirect-manual.md` — линии поддержки L1/L2 (L3 убрана);
- сами инструкции агенту — только через `read`.

Инструментов у агента два (второй — только когда нужен перевод):

**`read(manual, section_id)`** — читает раздел: заголовок, путь от верхнего раздела,
список подразделов (`children`) и полный `text` (в нём markdown-таблицы и ссылки на картинки —
плейсхолдер `__IMG_PREFIX__` заменяется на `/ml-assets/image`, см. ниже).
`manual` — slug из оглавления (`supplier-portal`, `customer-portal`, `mvc-supplier`,
`offer-ste-creation`, `bulk-price-list-import`, `supplier-portal-econtract`),
`section_id` — номер слева от двоеточия. Если вместо id передали заголовок,
инструмент подберёт похожие разделы и вернёт список id. Есть в базовом агенте.

## Перевод на линию поддержки

Мануал `support-redirect-manual.md` описывает две линии (L1 — информационная,
L2 — экспертно-методологическая; L3 убрана) и куда какие обращения переводить.
Он целиком кладётся в системный промпт (`support.load_lines_manual()`) — отдельного
инструмента `support_manual()` больше нет.

**`transfer_to_support(line, reason)`** — переводит обращение и **закрывает чат**.
Принимает `L1`/`L2` (терпимо к `l2`, `2`, «линия 2»). Дальше в чат писать нельзя:
API отвечает `409`, в админке вместо формы появляется плашка. Реального интерфейса
оператора нет — это заглушка (`support.py`).

Логика в системном промпте:

1. Найти раздел в оглавлении (поиск не нужен, оглавление полное).
2. Если в базе знаний ответа нет → `transfer_to_support(...)` — мануал по линиям уже в промпте.
3. Если вопрос вообще не про Портал и ни одна линия не подходит → **не переводить**,
   а вежливо сказать, что это не по теме.

Состояние перевода хранится в чате: `redirect_line`, `redirect_reason`, `closed_at`
(видны в `GET /ml-api/chat/<id>`); в SSE приходит событие `redirect`,
а `POST .../message` для закрытого чата отвечает `409`.

LLM: локальная модель в LMStudio (`LMSTUDIO_MODEL`, `LMSTUDIO_API_BASE`,
`OpenAILike`). Каждый ответ — трейс в Langfuse
(`chat-response`, `session_id` = id чата), инструменты и токены видны в админке карточками.
